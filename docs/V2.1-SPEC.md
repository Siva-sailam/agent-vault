## Part A — editable weekly limit (policy server)
New admin endpoint (localhost only, same CORS as the others):

    POST /v2/agents/:pubkey/budget   body { "weeklyBudget": <integer> }

Validation:
- whole number, 1..10000 (aUSD has 0 decimals) -> else 400 { error: "InvalidBudget" }
- unknown agent -> 404 { error: "AgentNotFound" }

Semantics (state these in the README):
- Takes effect immediately for the CURRENT window: remaining = new budget - spent.
- Lowering below what is already spent -> remaining 0. No clawback, no window reset.
- Pending reservations count as spent (same as authorize does today).
- The budget is a LIMIT, not money: the vault balance still caps real spending.

Audit: new table rule_changes (id, agent, field, old_value, new_value, changed_at).
Every budget change writes one row, in the same SQLite transaction as the update.
GET /v2/state includes the last 20 rule_changes.

Concurrency: run the update inside a SQLite transaction so it cannot race authorize.

## Part B — control panel: V1 | V2 switch, V2 with V1's look and feel
1. SWITCH
   - A V1 | V2 segmented switch at the top of the control panel, same style as the
     storefront's V1 | V2 switch. Default = V2 on every page load.
   - V1 = today's carousel exactly as it is now, minus the old V2Card page.
   - Small subtitle under the switch:
     - V1: "Rules on-chain. Changes need a Phantom signature."
     - V2: "Rules off-chain in the policy server. Changes are instant and free."

2. LOOK AND FEEL — V2 must be visually indistinguishable in style from V1
   - REUSE the existing V1 components and CSS (PhoneFrame, CardCarousel, the
     MainWalletCard layout, the AgentCardView card face, ApprovalModal, App.css,
     panel.css). Do not invent new colours, fonts, spacing or card shapes.
   - Prefer extracting shared presentational pieces (card face, budget bar,
     merchant toggle row, revoke button, balance hero) so V1 and V2 render through
     the same components with different data/actions. V1 output must stay pixel-same.
   - Only visual difference allowed: a small "V2 · off-chain policy" tag on V2 cards.

3. V2 VIEW — same carousel, driven by GET /v2/state
   Page 1 — V2 main card (mirrors V1 MainWalletCard):
   - "Main wallet": the owner's aUSD balance (owner ATA), as in V1.
   - "Vaults": Food vault balance and Shopping vault balance, each with a Solscan link.
   - "Move money":
     - Deposit: pick vault (Food | Shopping) + amount -> ONE Phantom-signed transaction:
       TransferChecked(owner ATA -> chosen V2 vault, mint aUSD, decimals 0),
       authority = owner, fee payer = owner. No multisig, no server, no agent.
       Block amounts above the main-wallet balance before asking Phantom.
     - Withdraw: pick vault + amount -> reuse the existing recovery flow
       (useRecoveryAction + agent-service /v2/recovery/cosign, owner + agent sign,
       destination = owner ATA only). Button "Withdraw to my wallet", hint:
       "Needs 2 of 3 signatures: you + the agent. The policy server is not involved."
   - Use the existing ApprovalModal for both (pending / success + Solscan / error).
   - No "Create your vault" and no "New agent" in V2 (out of scope; note in README).

   Pages 2 and 3 — one card per V2 agent (Food, Shopping), mirroring V1 AgentCardView:
   - Card face: logo, name, Active / Revoked, BLOCKED stamp when revoked.
   - Spent / budget bar, "X left", window reset time.
   - NEW "Weekly limit" number field + Save -> POST /v2/agents/:pubkey/budget.
     Show the server's error text if refused; refresh state after success.
   - Merchant toggles and Revoke / Unrevoke via the existing admin endpoints.
   - If the policy server is down: show "Policy server unavailable on :4031" in place
     of the rule controls. Deposit and Withdraw still work (they don't need it).

4. Remove the old V2Card page once the V2 view covers everything it did.

## Tests (local only, no devnet)
policy-server:
- raise budget -> an authorize that previously failed BudgetExceeded now passes
- lower budget below spent -> remaining 0 -> next authorize BudgetExceeded
- invalid values (0, -5, 1.5, "abc", 10001) -> 400 InvalidBudget
- unknown agent -> 404 AgentNotFound
- each change writes exactly one rule_changes row with correct old/new values
- budget update racing an authorize -> never approves more than the budget in force

All existing tests (policy server 17, agent service 10) must still pass.
app: `npm run build` must succeed with no type errors.
